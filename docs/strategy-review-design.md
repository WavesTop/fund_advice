# 复盘与策略改良开发方案

- 更新日期：2026-09-19
- 对应范围：整体技术架构 §3.5
- 实施计划：[复盘与策略改良分阶段开发计划](strategy-review-plan.md)
- 当前结论：复盘、笔记、策略版本差异和显式启用／恢复已存在前端演示；系统性问题识别、候选修订、独立验证、正式采用及后续观察尚未实现。固定样例不能证明策略有效。

## 1. 目标与边界

本阶段把 §3.3 的建议和 §3.4 的决定、真实操作、模拟执行及结果组织成可复查证据，分别检查系统策略和用户自身方法，提出可证伪的改良候选，并在独立数据与后续真实时间中检验改动是否有效。

本阶段包含：

- 按单次决定、周期、基金、策略版本和时间区间复盘；
- 从多条记录中形成问题线索，保留支持、反对和资料缺口；
- 管理原策略、候选版本、差异、适用条件和采用记录；
- 冻结验证协议，比较原方案、候选方案和必要基线；
- 本人显式启用、恢复及后续前瞻观察；
- AI 可选地生成问题假设和解释，但不得独自决定启用或改写结果。

本阶段不负责市场数据采集、账本核算、交易模拟或真实交易。它只消费不可变输入并产生新的复盘、候选、验证和采用对象；发现底层账本错误时，要求 §3.4 追加更正并生成新复盘版本，不直接修改事实。

## 2. 当前实现基线

| 已有能力 | 当前性质 | 正式化缺口 |
| --- | --- | --- |
| 收益与复盘页面 | 支持收益、时间线、单次决定、复盘笔记和策略改良标签。 | 收益和问题内容为固定演示样例。 |
| 决定下钻 | 可按决定筛选关联演示交易，并展示更正说明。 | 没有正式建议、模拟、比较及证据对象。 |
| 复盘笔记 | 可保存浏览器本地草稿。 | 无后端版本、证据附件、关联对象和审计时间。 |
| 策略 v1.0／v1.1 | 展示候选差异、验证说明、显式确认启用和恢复。 | 仅两个固定版本；没有策略定义、验证报告或真实运行影响。 |
| 采用历史 | 启用和恢复均追加事件，旧决定保留原建议版本。 | 仅 `localStorage` 演示状态，未参与正式建议生成。 |

## 3. 复盘对象与证据原则

### 3.1 两类被复盘对象

- **系统策略**：有明确规则、参数、证据模板和实现版本，可进行历史和前瞻比较。
- **用户方法**：由决定理由、操作习惯和用户明确描述形成。只有能表达为可执行规则的部分才可进行策略对照；否则只形成问题假设和观察建议。

不得因一次亏损认定策略失效，也不得因一次盈利认定判断正确。复盘至少展示样本数量、观察区间、涉及周期、市场环境、数据覆盖和不确定性。

### 3.2 事实、归因线索和结论分层

| 层级 | 示例 | 约束 |
| --- | --- | --- |
| 已观测事实 | 决定晚于建议 3 天、模拟订单因限购跳过、实际费用更低。 | 可回到 §3.4 事件、比较或来源。 |
| 归因线索 | 时点延迟可能解释部分差异。 | 同时保留反例、残差和其他可能原因。 |
| 问题假设 | 短期策略的入场条件可能对高波动阶段过敏。 | 明确受影响范围和可证伪条件。 |
| 改良候选 | 增加波动门槛并延长冷却。 | 必须形成版本差异和独立验证协议。 |
| 验证结论 | 独立样本风险下降但收益无改善。 | 报告基线、成本、样本和多次试验，不只给“更好／更差”。 |

### 3.3 时间与版本隔离

复盘运行引用固定建议、策略、个人条件、账本、模拟、比较和市场输入版本，并保存生成时点。底层发生更正时创建新的复盘运行并显示差异；旧报告仍按原输入可读。

候选修订使用的数据称为开发区间；最终评价使用未参与修订的验证区间。前瞻观察必须在候选及协议冻结后开始，不能回填错过的建议或把离线补算冒充当时发布。

## 4. 领域模型

| 对象 | 关键内容 |
| --- | --- |
| `review_run` | 范围、周期、输入快照、生成时间、方法版本、状态和覆盖。 |
| `review_note_revision` | 用户笔记、已观测事实／假设标记、关联对象、证据及修订链。 |
| `issue_hypothesis` | 受影响对象、问题类型、支持／反对证据、样本、严重度依据、失效条件。 |
| `strategy_definition` | 策略家族、可执行规则结构、适用范围、输入输出契约和所有者。 |
| `strategy_revision` | 父版本、完整配置、实现／提示版本、变更摘要、理由和创建时点。 |
| `candidate_revision` | 来源问题、预期作用、取舍、适用条件、开发数据边界和状态。 |
| `validation_protocol` | 冻结基线、指标、区间、样本切分、费用执行政策、成功／停止条件。 |
| `validation_report` | 所有预定指标、覆盖、失败结果、敏感性、多次试验信息和结论等级。 |
| `strategy_adoption_event` | 本人确认的启用／恢复、目标版本、生效时间、影响范围和理由。 |
| `forward_observation` | 冻结版本的真实生成记录、成熟度、后续结果和失效状态。 |

策略修订必须保存完整可运行定义，不只保存文字差异。恢复旧版本通过新的采用事件将其重新设为后续生效版本，不能回写过去生效区间。

## 5. 复盘分析

### 5.1 复盘视图

支持四种互补入口：

1. 单次决定：对照建议、决定、实际与模拟执行、费用和结果。
2. 周期／期间：观察同类决定的重复模式和持续表现。
3. 策略版本：比较版本内结果、覆盖、弃权和风险。
4. 用户方法：分析采纳、延后、自主交易、仓位和费用习惯，但不进行人格化评价。

差异维度至少包括时点、基金选择、仓位、现金使用、费用、执行限制、数据缺失和未解释残差。系统不得把相关性描述成因果，也不得仅挑选支持某一候选的记录。

### 5.2 问题线索生成

本地规则先完成可重复的聚合与门槛判断；门槛、最小样本和观察窗口全部版本化。AI 可在固定证据包内提出解释、反证和待查项，输出必须引用对象 ID，经过结构及数字校验后才可进入候选区。

任何线索都需同时给出：受影响对象和周期、观察数量、影响大小、支持证据、反对证据、资料缺口、可能原因、替代解释和下一步可验证条件。证据不足时状态保持 `insufficient_evidence`。

## 6. 候选策略与验证

### 6.1 候选生命周期

`draft → ready_for_validation → validating → observed`，随后只能进入 `rejected`、`inconclusive`、`eligible_for_adoption` 或 `expired`。状态改变追加事件并说明依据；验证失败不得删除候选或修改预设成功条件。

候选至少说明：修改了什么、为什么可能有效、可能损失什么、适用／不适用场景、与哪些问题相关、需要哪些数据、如何失败以及如何恢复。

### 6.2 独立验证

验证协议在运行前冻结：

- 原版本、候选版本及朴素基线；
- 开发、验证和前瞻区间及成员集合；
- 资金、外部现金流、费用、成交延迟和不可成交政策；
- 收益、回撤、波动、换手、费用、覆盖、弃权和稳定性指标；
- 主要指标、最低样本、成功／失败／证据不足条件；
- 已进行的候选和参数尝试数。

同一数据上反复改参必须记录为多次试验；重叠持有窗口、幸存者偏差、历史成分、资料发布时间和 AI 后见知识单独检查。候选可以改善风险但降低收益，页面必须展示完整取舍。

### 6.3 本地与 AI 对照

若候选含 AI 分支，应在相同输入、执行和成本口径下比较本地规则、AI 分支及融合分支。文字更流畅、理由更长或约束校验通过都不是投资效果证据。历史无法重建当时模型知识时，该分支只能标为事后试验。

## 7. 采用、恢复与前瞻观察

### 7.1 显式采用

只有本人可触发采用。确认页展示目标版本、验证等级、证据限制、差异、生效时间、影响的后续建议／模拟以及恢复方式。采用接口要求幂等键和目标版本状态检查；过期、验证不足或依赖缺失时不可启用，并返回原因。

采用只影响生效时间之后的新建议和新模拟。历史建议继续引用原策略版本，正在运行的冻结试验不自动切换版本。

### 7.2 恢复

恢复是一次新的采用事件，目标可以是已知可运行的旧版本。恢复前检查配置、代码和数据依赖仍可用；无法完整恢复时禁止伪成功。恢复不删除候选、验证报告或新版本历史。

### 7.3 持续观察

采用前后均可启动预先登记的前瞻观察。短、中、长期分别判断样本成熟度；未完成所需持有窗口时只显示观察中。版本变化启动新的观察组，不与旧组拼接冒充连续验证。

观察如实报告改善、恶化、失效和证据不足。触发风险条件可暂停新建议，但自动启用另一候选仍不允许。

## 8. 服务接口

| 接口 | 用途 |
| --- | --- |
| `POST /api/v1/reviews` | 按冻结范围创建复盘运行。 |
| `GET /api/v1/reviews/{id}` | 读取事实、线索、覆盖及输入引用。 |
| `GET/POST /api/v1/review-notes` | 查询或追加带关联的笔记修订。 |
| `GET/POST /api/v1/issues` | 查询问题线索；人工确认只改变状态，不改证据。 |
| `GET/POST /api/v1/strategy-revisions` | 读取原版本或创建候选修订。 |
| `POST /api/v1/validation-protocols` | 冻结验证协议。 |
| `POST /api/v1/validation-runs` | 运行既定协议；长任务交给 §3.6。 |
| `GET /api/v1/validation-reports/{id}` | 返回完整指标、覆盖和限制。 |
| `POST /api/v1/strategy-adoptions` | 本人显式启用或恢复。 |
| `GET /api/v1/forward-observations` | 查询观察成熟度和结果。 |

所有历史读取按具体 ID 和版本返回。候选修改创建新修订；验证协议冻结后不可编辑，只能复制为新协议。

## 9. 页面接入

现有“收益与复盘”中的收益对比、决策时间线和策略改良结构可复用：

- 复盘笔记接正式版本与对象关联，允许标注事实、假设和待验证项；
- 问题卡片显示系统策略／用户方法、周期、样本、支持／反对证据和缺口；
- 版本详情展示结构化差异、协议、开发／验证区间和全部指标；
- 启用和恢复保留双重确认，但改为调用正式采用服务；
- 演示 v1.0／v1.1 继续仅在显式演示模式出现，不与真实版本混排；
- 新数据或底层更正出现时提示创建新复盘，不静默更新旧报告。

## 10. 测试与验收

### 10.1 必测场景

- 单次亏损但长期样本不足，不产生“失效”结论；
- 实际优于模拟、用户未采纳反而更好、模拟无法成交等结果均如实进入复盘；
- 同一事件被多条建议引用时不重复计样本；
- 候选使用开发数据改善，但独立验证恶化或无显著信息；
- 多次试参、重叠窗口、幸存者样本和未来资料注入被识别；
- AI 生成无引用原因、错误数字或事后知识时被拒绝或降级；
- 重复启用、过期候选、运行中版本切换和恢复依赖缺失；
- 备份恢复后旧报告、候选、采用历史和原建议引用完整。

### 10.2 完成条件

任一问题和修订都能回到原始记录；任一验证报告能由冻结协议和输入复现；失败及证据不足结果保留；采用和恢复由本人显式确认且只影响后续；前瞻观察不回填。完成工程不等于策略已证明有效，策略等级必须依实际证据单独报告。

## 11. 隐私与表述

用户理由、资产和复盘笔记默认不发送给 AI。确需发送时由 §3.6 显示资料类别、服务商和用途，并最小化内容。页面避免“你判断错误”等归责语言，使用“在这些记录和口径下观察到……”并公开样本和替代解释。
