# 本地运行与工程保障：分阶段开发与复查计划

- 更新日期：2026-09-19
- 对应范围：整体技术架构 §3.6
- 设计依据：[本地运行与工程保障开发方案](local-runtime-engineering-design.md)
- 当前进度：开发运行和若干可靠性原语已存在，日常可交付运行链路未完成。以下把“基础已实现”和“正式阶段通过”分开标记。

## 1. 状态规则

| 状态 | 含义 |
| --- | --- |
| 未开始 | 尚无本项实现。 |
| 进行中 | 已有部分可复用实现，仍缺正式退出条件。 |
| 待复查 | 实现、自动验证和交付说明完成，等待用户复查。 |
| 已通过 | 用户已接受正式交付。 |
| 已完成（开发基础） | 已实现可复用的开发／底层能力，但不是完整日常功能。 |
| 已完成（演示） | 仅有明确标识的页面样例。 |
| 受阻 | 外部环境或上游契约使本项无法完成。 |

运行保障阶段可以并行提供其他模块所需的任务、备份和配置能力，但不能借此修改业务规则。每项交付包含受支持环境、配置变化、故障验证、数据保护和最短人工复查步骤。

| R2.6 任务页面正式接入 | 未开始 | R2.5。 | 用真实任务 API 替换演示队列，展示状态、阶段、数量、错误和可用操作。 | 刷新／重启后状态一致；重复发起定位原任务；取消请求不提前显示已取消。 |

大阶段退出条件：长任务在断网、休眠、退出和重启后状态可解释且不会重复产生业务结果。

## 11. 推荐顺序

优先顺序为 `R0 → R1.1/R1.2 → R2 → R4 → R1.3/R1.4 → R5 → R6 → R7`；R3 可在 AI 正式接入前独立推进。§3.4 的长模拟依赖 R2，正式账本写入前至少完成 R4.1/R4.2；§3.5 前瞻跟踪依赖 R2 和 R5。

每次复查同时检查正常路径和一个故障路径。只有 R0–R7 的正式退出条件全部满足后，§3.6 才能标为完成；R-BASE 和 R-UI 仅说明无需重复实现的基础与演示成果。
