# 板块数据采集修复与本地验收

本说明对应 `sector-source-repair-v1`，补丁基线为 `5a2b542a11f0c0db63537524bf53f96d2ff24e98`。修改采集和诊断，不修改交易日历、评分门槛、现有迁移或依赖锁文件，也不把缺项填零。

## 1. 来源与排序规则

行业模式完整读取同花顺行业目录。所有目录成员都进入覆盖分母；日线失败、成分失败，均不能成为剔除行业的理由。测试只替换传输，不再改变行业范围或来源选择。

目录和成分请求明确携带 `np=1`、`fltt=2`、`invt=2`。除数组外，仅接受连续数字索引的 `diff` 对象；总数漂移、重复身份、缺页仍拒绝。主端点失败时在同一供应商的备用端点重新读取整个数据集，不拼接不同端点的分页。

日线按同花顺原生行业代码读取；请求截止日是项目日历给出的最新完整交易日，不被陈旧的成交额日期截短。仅同身份、同来源的真实已存日线可补内部缺口；不能前向填充、插值，也不能用缓存较新的尾部冒充本轮已更新。各行业无法提供121条而有真实、连续、当期的较短序列时保留它，只由足够长度的周期参与分析。

同花顺行业目录、行业日线和行业摘要属于同一供应商，不是独立第三方佐证；其实际可用性以本地运行文件为准。旧跨源序列保留作历史参考，但不参与当前排名。

前端只对当前合格周期排序。没有可排名数据时，明确提示暂按代码展示；有部分合格数据时显示合格数和末尾未排名数。不得用历史涨跌幅伪造当前排名。三个周期的真实榜单可能相同，不以“顺序必须不同”作为验收条件。

## 2. 财报和估值任务

只有当前同花顺行业成分股通过后，才允许股票财务和行业估值进入采集队列。若同花顺成分页返回403或成分身份未通过，财务阶段发布缺项状态，不请求替代供应商。行情／成分阶段和财务阶段分别有界，完整行业刷新使用更温和的请求节奏，仍受现有网页工作进程900秒上限约束。

这不是无限重试或稳定性承诺：网络慢时单表仍会超时，但不能因为前一表耗尽预算就把后面的表全部假报为空。每个数据集记录状态、请求日期、行数、排除数、预算、耗时、错误和原文引用。解析、分页失败仍保留已经归档的原响应；空成功响应记为缺失，不记为可用数据。

本补丁没有实现跨次财报缓存、发行人原文替代接口、历史估值自动回补或行业催化采集。后续应依据诊断中的具体表、证券、字段、缺失日期逐项补充，不能把这些未实现内容写成已验收能力。

## 3. 应用补丁

先停止旧前后端服务，并按项目已有一致备份方式备份日常 SQLite。不要只复制 WAL 模式的主文件。将包内 `sector-data-repair.patch` 放到仓库根目录，执行：

```bash
git rev-parse HEAD
git status --short
git apply --check sector-data-repair.patch
git apply sector-data-repair.patch
```

`--check` 失败时停止，不要用强制覆盖或回退已有修改来绕过冲突。补丁没有数据库迁移，不需要重复应用旧迁移或导入测试夹具。此前存在的运行中任务仍按项目原有规则处理，不能未经确认自动解除进程互斥。

## 4. 一条命令生成真实运行包

在仓库根目录运行：

```bash
uv run --locked python -m scripts.verify_sector_data
```

此默认模式不要求先手动启动服务。脚本用本次代码启动一个随机本机端口的 API 和**新的临时隔离数据库**，依次调用真实 `/api/sectors/refresh`、分析接口和各板块实际 `/series` 接口。它不注入模拟采集器；完成后关闭自己启动的服务并清理临时数据库，保留诊断 ZIP。

**隔离库的结果不会写入网页日常数据库。** 要刷新当前网页使用的库，先按原方式重新构建／启动本次代码的前后端，再运行以下模式（端口按实际后端调整，不要填前端页面地址）：

```bash
uv run --locked python -m scripts.verify_sector_data --base-url http://127.0.0.1:8000
```

该模式会像点击“重新评估”一样写入该服务的数据库。运行时不要同时点击页面刷新或启动另一个同目标采集。需要只导出既有资料、不再采集时使用：

```bash
uv run --locked python -m scripts.verify_sector_data --base-url http://127.0.0.1:8000 --read-only
```

只读导出不能当作本轮实时来源验收。首次运行安装依赖由 `uv` 处理；依赖安装本身失败、尚未进入 Python 脚本时，需要保留终端错误文本。

## 5. 诊断文件与验收含义

默认输出 `runtime/sector-verification-<UTC时间>-<随机后缀>.zip`，终端会打印完整路径。不会覆盖旧诊断包；可用 `--output 新路径.zip` 指定新文件。

| 文件 | 核验内容 |
| --- | --- |
| `SUMMARY.md`、`analysis.json` | 完整行业分母、短中长期合格数及顺序、每板块各类缺项；核心数据与研究证据分开判定 |
| `refresh.json`、`collection.json` | 真实刷新响应、同一个采集任务的终态、每次上游请求和错误；HTTP 200不直接视为成功 |
| `evaluation.json`、`series.json`、`series-checks.json` | 应用实际数据、日线网格，以及从实际日线重新计算的收益、均线偏离和最大回撤 |
| `raw-manifest.json`、`raw/` | 本次任务关联的公开原响应、来源地址和SHA256核验；失败JSON也保留 |
| `metadata.json`、状态文件、`server.log`（隔离模式） | 采集版本、相关代码哈希、日历、环境版本、启动异常，以及导出期间是否发生新任务 |

价格复算允许展示四舍五入误差，但不允许缺少交易日。排序核查考虑展示收益已经四舍五入，不能将同样显示值下的不同原始收益误判为排序错误。财报按完整成分分母检查；零／负基期导致同比不可计算，不等于实际金额没有取得。

长期估值至少60次、跨度365日的原条件保持不变；催化资料未接入仍是缺项。脚本不会通过改成“支持样本全覆盖”、缩小行业池、伪造历史时点或隐藏长期要求来让验收变绿。

退出码：`0` 表示本次核心数据、长期研究证据、实际日线复算、任务一致性及原文导出检查均通过；`1` 表示已成功生成诊断包，但仍有缺项或本次不是实时采集；`2` 表示启动或运行未完成。**出现1或2仍发送已经生成的ZIP，不要仅因为非零退出码就反复重跑。** 这些检查不验证投资收益或正式推荐有效性。

原文默认最多400个资产、64MiB，日线导出和原文导出各最多120秒。超过预算的项目在清单中明确标记，没有导出的原文不声称已核验；参数 `--max-assets`、`--max-raw-mib` 可在有针对性的二次核验时调整。包中不主动包含完整数据库、持仓、`.env`、凭据或其他项目文件；错误文本会脱敏常见令牌和用户主目录，但分享前仍建议检查可能含本机路径的日志。

## 6. 回归范围

新增三组 Python 定向回归：来源身份／失效回退、独立数据集预算／原文保留、验收脚本／日线复算／诊断导出。对应命令：

```bash
uv run --locked python -m unittest discover -s tests -p 'test_sector_*repair.py'
```

前端 `sector-ranking-state.test.ts` 使用仓库既有 Vitest 配置；不增加新依赖。定向测试中的行情、财报和本机HTTP服务均为明确的合成夹具，不能用这些测试结果证明任一上游端点可用或实际数据齐全。正式全仓回归、前端构建、浏览器和真实来源覆盖需在具有完整项目与锁定依赖的本地环境继续运行。
